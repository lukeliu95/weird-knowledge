### 内容要点（模型概括，不是原文）

**要解决的问题**

harness（外壳）是包在大模型外面的可执行代码，规定提示词、工具和执行流程。现有的自动优化方法（Meta-Harness、AHE 等）用执行反馈去改代码，但最后只挑出一个"全局外壳"给所有任务用。问题是任务五花八门，对一类任务有用的改动，对另一类可能有害：AHE 自己的拆解实验就发现加记忆对难题有用、对简单题反而变差；EvoHarnessBench 也发现加工具、加 skill、加专家 agent 会把原来好用的行为弄坏（第 1 节）。

**核心想法**

1. 外壳既然是代码，就用面向对象的写法组织：一个基础外壳当父类，每个专用外壳是它（或另一个专用外壳）的子类，可以覆盖父类的方法、也可以加新方法；共享的行为靠继承复用，不用复制（第 1 节、第 3.2 节）
2. 训练时按"执行上的共同需要"给任务分组，每次只针对一组写一个子类、只在这一组上考，分数比现任高才收下。这样不用每改一次就把全部训练题重跑一遍，也不会把一组的改动强加给别的组（第 1 节、第 3.4 节）
3. 测试时先让基础外壳跑一遍，再由一个"路由"模型看任务、看这次的执行记录、看训练时攒下的"路由经验"，决定换哪个专用外壳重跑，或者直接保留基础外壳的结果（第 3.5 节）
4. 外壳结构、路由经验在测试前冻结，执行任务的模型权重全程不变；训练题和测试题完全分开（第 3.1 节，作者特意指出 Meta-Harness 原文有一个实验是拿同一批题搜索又评测）

**主要方法**（第 3 节，附录 A.4）

| 步骤 | 做什么 |
|---|---|
| 起步 | 基础外壳跑一遍训练题，按执行记录里看出的共同需要分组 |
| 每一轮 | 负责进化的 agent（编程 agent，能读代码、执行记录、派 subagent）选一组和一个父类，找出"一个这组共有、能靠外壳修的机制"，写一个子类，调用 `super()` 保留父类行为；明确不许写死任务编号、答案、文件名 |
| 收不收 | 这组分数高过现任、且通过各测试集自己的验收检查才收；收下的进入家族树，可以成为这组的现任外壳 |
| 调整 | 一组屡次被拒就降低它的搜索优先级；分组本身每轮重审，可以拆、可以合 |
| 攒经验 | 执行记录总结成两种经验：设计经验（什么改法管用、什么试过不行）给写代码用，路由经验（什么情况该用哪个外壳）给路由用 |
| 路由 | 输入是任务、基础外壳这次的执行摘要（调了哪些工具、报了什么错、写了几次）、外壳目录和路由经验；没有明显合适的就选基础外壳 |

**专用外壳的实际例子**（第 5.2 节，附录 A.4.3、B）

| 外壳 | 解决什么 |
|---|---|
| 写 Word 文档 | 基础外壳把纯文本写进 .docx 文件名，得到的不是真 Word；子类改写文件写入，把文本渲染成真的二进制文档，失败就退回父类写法（附录 B.1） |
| 补"漏写"检查（三代） | s9：任务需要改数据却一次写入都没做时，要求再来一轮；s12 继承它，快到轮数上限还没写成功就提醒；s29 再继承，加上遇到无法恢复的报错时的纠正提示（附录 B.2，图 9） |
| 表格百分比 | 父类提醒"存算好的值，不要存公式字符串"；子类继承后再加一步：收尾前读存好的表，把标着百分比、值在 0 到 1 之间的格子挑出来，要求改一次（附录 A.4.3、B.3） |
| 接口报错整理 | 执行记录里反复出现查询语句解析错误时，路由经验指向这个外壳，它把报错改写成"怎么修查询"的提示（第 5.2 节，图 6c） |

**实验设置**（第 4.1 节，附录 A.1、A.2）

- 三个长任务测试集：AutomationBench（业务流程，训练 300 题、测试 300 题）、Workspace-Bench（跨文件和应用的办公任务，训练 288 题、测试 100 题）、Toolathlon-GYM（多工具任务，训练 251 题、测试 252 题）
- 执行任务的模型统一是 gemini-3.5-flash；所有外壳优化方法的进化 agent 统一用 Claude Opus 4.8，最多 40 轮；路由主实验用 Claude Sonnet 5
- 对照：不进化的基础外壳；全局优化 Meta-Harness、AHE；按任务类型各练一个专用外壳的 AAH（同期工作）；以及"多花推理"的做法：基础外壳跑 2 次或 5 次挑最好的、跑一次后自我修改再跑一次
- 主表每个方法跑 3 次，报均值和标准差

**需要说清楚的边界**

- 测试时每道题都要先跑一遍基础外壳，被路由到专用外壳的（AutomationBench 那次是 55.3%）还要再跑一遍，外加路由模型的调用。表 1 的"步数"只算最后选中的那次执行，不含基础那次和路由调用，所以"步数最少"不等于"总花费最少"。作者用"多花推理"的对照组来回应这一点，但没有报每道题的总调用次数或总费用（第 4.1 节，表 1 说明）
- 和同期的 AAH 比，领先幅度不大：Workspace-Bench 39.48±3.21 对 38.62±2.98，Toolathlon-GYM 37.45±0.98 对 AHE 的 36.23±1.19，都在一个标准差左右；拉开明显差距的是对全局外壳的方法
- 路由拆解（表 2）、继承拆解（图 5）、陌生任务实验（图 7）都只跑了一次，没有误差范围；继承拆解只在 Workspace-Bench 上做
- 陌生任务实验说明的是"不会变差"，不是"能变好"：路由全部选了基础外壳，等于什么也没用上
- 执行模型、进化 agent、路由模型都是固定的一套（Gemini 执行，Claude 进化和路由），换别的模型效果如何没测
- 作者写的局限只提到依赖外部接口（服务宕机、限流、接口变动、密钥和权限配置），没有讨论上面这些评测口径上的问题
- 预印本，尚未同行评审；文中模型名（gemini-3.5-flash、Claude Opus 4.8、Claude Sonnet 5）照论文写。附录 A.4.2 写路由默认用 Sonnet 5 检索、Opus 4.8 选择，第 4.1 节写主实验路由用 Sonnet 5，表 3 的案例用 Opus 4.8，三处说法不完全一致
- 作者声明用 AI 工具协助改写论文、检查代码和做图（附录 A.8）

## 溯源

- 核心主张：不同任务需要的 harness 改动会互相冲突，只优化一个全局 harness 不够；把 harness 写成面向对象的类层次，按任务的共同执行毛病分组、每组进化一个继承基础外壳的子类，测试时先跑基础版、再看执行记录把题目路由到合适的子类，分数更高、搜索更快。
