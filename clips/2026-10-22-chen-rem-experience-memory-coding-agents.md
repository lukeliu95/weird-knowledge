### 内容要点（模型概括，不是原文）

**要解决的问题**

编程 agent 一次修 bug 要走几百步，留下几万到十几万 token 的过程记录，但下一次几乎不复用。已有的记忆系统都在拼"找得准"：从过去的记录里检索最相关的那一条。作者认为这不是卡住的地方（第 1 节）：

- agent 只用得上塞给它的一小部分上下文（Zhu 等 2026）
- 无关或位置不对的上下文会拖后腿（Shi 等 2023；Liu 等 2024）
- 抽象的经验比细节迁移得好，详细的过程记录在难题上反而有负作用（Hu 等 2026）

共同的原因是：检索那一刻看不见正在干活的 agent 是什么状态，所以决定不了"它现在需不需要这条经验、什么时候给、给多久"（第 1、3.1 节）。

**核心想法**

把经验记忆当成"控制问题"而不是"查找问题"：在 agent 的"想一步、做一步"循环里，明确做三个决定（第 1、3 节）：

| 决定 | 做法 | 出处 |
|---|---|---|
| 存什么 | 每条做完的记录压成一份按四个阶段（定位、理解、修法、验证）排好的文档，平均约 270 token，比原记录小两个数量级。这份文档既是检索单位，也是直接塞给 agent 的内容 | 第 3.2 节 |
| 什么时候给 | 文档在任务一开始就给；代价更高的"实现记录"（那次的原始改动和验证，最多 1.2 万字符）先扣着，等 agent 第一次验证失败（说明它自己的路走不通）才给 | 第 3.2 节，附录 B |
| 什么时候忘 | 实现记录只出现一次，下一轮就撤掉；四阶段文档一直留着 | 第 3.2 节，附录 A |

作者的说法：前人把力气花在"哪一条"，这篇换成"什么时候"（第 1 节）。

**主要方法**

| 项 | 设定 | 出处 |
|---|---|---|
| 写入 | 原始记录 5.5 万～17 万 token，先去掉工具返回的结果（约缩小 15 倍），再用一次模型调用抽出几个字段（改了哪些文件、函数、根因、修法、测试），由固定程序排成四阶段文档 | 第 3.2 节 |
| 读取 | 用现成的文本向量模型（亚马逊 Titan v2）找最像的 5 条，再用一次模型调用重排，取第一 | 第 3.2 节，附录 D |
| 字段自动生成 | 不用手写抽取提示词：拿 9 条示例记录，让模型写提示词、另一个模型按 5 个维度打 1～5 分、弱项再改，最多 5 轮。编程领域第一轮就达标 | 第 3.3 节，附录 G |
| 基准 | SWE-ContextBench Lite：99 道仓库级修 bug 题，300 条已解决的记录当经验池，每题标了一条"相关记录" | 第 4 节 |
| agent | Strands 框架，6 个工具，每题独立 Docker，最多 100 轮，不截断对话历史；默认用 Claude Sonnet 4.5，第 5.5 节换 5 个模型 | 第 4 节 |
| 怎么算成本 | 按 token 类型加权（新输入×1、写缓存×1.25、读缓存×0.1、输出×5，按 Anthropic 的价目比例） | 图 2 |
| 测"读没读" | 从塞进去的文字里抽出文件名、函数名，看 agent 自己的话和工具调用里出现了多少，叫"覆盖率"。只证明"出现过"，不证明"因为它才做对" | 第 3.3 节 |
| 重复次数 | REM、不给记忆、几种召回变体各跑 3 遍（共 297 次配对）；其他条件只跑 1 遍，只看方向 | 第 4 节 |

**主要结果**

| 结果 | 数字 | 出处 |
|---|---|---|
| 检索更准 | 第一名就是那条相关记录的比例 68.7%；现有最好的 LangMem 55.6%，OpenViking 38.4%，Mem0 25.3%，Supermemory 23.2%，agent 自己翻原记录 22.2% | 第 5.2 节、表 1 |
| 准在"结构"不在"长短" | OpenViking 的片段约 246 token，和四阶段文档差不多长，只有 38.4%；只用向量相似度不重排，四阶段文档已经 62.6%，比 LangMem 高 7 个点 | 第 5.2 节 |
| 自动生成的字段不比手写差 | 手写 66.7%，自动生成 68.7%（自动生成那版有 33 条因接口限流没抽出来，按没命中算） | 第 5.2 节，附录 D |
| 修复率小幅提高，三遍都赢 | 27.6% 对不给记忆的 24.9%（+2.7 个点）；三遍分别解决 27、29、26 题对 23、26、25 题 | 第 5.1 节、表 4 |
| 但统计上不显著 | 297 次配对里 REM 独赢 20 次、不给记忆独赢 12 次，McNemar 检验 p=0.22。作者自己说只靠"三遍都赢"来撑这个结论 | 第 5.1 节 |
| 更便宜更快 | 每题加权 token 45.2 万降到 37.4 万（-17%）；平均 11.9 分钟降到 8.8 分钟；打不上去的补丁从 7 个降到 4 个 | 第 5.1 节、表 4 |
| 塞摘要或原记录没用，给对的也没用 | 5 种开局塞摘要或原记录的条件解决 22～24 题，不给记忆 23 题。基准原论文报的"给对的摘要从 26.3% 升到 34.3%"在这里没复现（23.2% 对 23.2%） | 第 5.1 节 |
| 塞原记录更贵 | 塞对的原记录，每题 token 从 45.2 万涨到 76.8 万，轮数从 70 降到 50，agent 拿它代替自己探索，但没多解决题 | 第 5.1 节 |
| 四阶段文档被读得最全 | 覆盖率：四阶段文档 69.1%，摘要 45.7%～52.5%，原记录 26.7%～27.2%，无关摘要 3.4%。四阶段文档比摘要还短（270 对 390 token），却被读全 1.5 倍 | 第 5.3 节、表 2 |
| 读得多的更容易做对 | 开局塞内容的几种条件里，做对的比做错的覆盖率高（效应量 d=+0.20，p=0.03）；但 REM 几种召回变体之间，覆盖率分不出对错（d=-0.06） | 第 5.3 节，附录 F |
| 卡住了再给，比一开始就给好 | 一开始就给实现记录 25.3%，卡住再给 27.6%；只有 58% 的任务真用到了实现记录，成本从 42.3 万降到 37.4 万 | 第 5.4 节、表 3 |
| 给完就撤，比一直留着好 | 一直留着 24.9%，撤掉 27.6%，三遍都是撤掉的赢；两者覆盖率几乎一样（50.3% 对 50.5%），差在它影响后面多少轮 | 第 5.4 节、表 3 |
| 真正起作用的是文档本身 | 完全不给实现记录、只给四阶段文档：26.9%，和 REM 只差 0.7 个点。作者说扣着、撤掉主要是"防止实现记录添乱"。表 3 里所有对比都没到 p<0.05 | 第 5.4 节、表 3 |
| 对最强的模型有害 | 5 个模型里，不给记忆时解决率 31.3% 及以下的 3 个从不变差（+4.0、+4.1、+1.0 个点）；47% 以上的 2 个在每种记忆条件下都变差 2.0～9.1 个点，Opus 4.8 从 47.5% 掉到 39.4%。换成"给对的文档"也一样，所以不是检索错了，是接收者的问题 | 第 5.5 节、图 3，附录 E 表 6～10 |
| 弱模型只吃得下摘要 | Haiku 4.5 只给文档 +4.0 个点，再加实现记录只剩 +1.0；作者推测别人的改动记录，只有会改编、不会照抄的 agent 用得上 | 第 5.5 节 |
| 字段能换到别的领域 | 同一个自动生成流程用在"自然语言转 SQL"的记录上，第一轮就达标，生成的 10 个字段和编程的完全不重合。只测了字段生成，没测完整流程 | 附录 G |

**作者的结论**（第 6、7 节）

- 经验复用的瓶颈不是"找得准不准"，而是经验存成什么样、在它的生命周期里怎么管
- 存的形式决定 agent 用上多少：同一条经验、同样的 token，按工作阶段组织就被读得更全
- 记忆不是越多越好：扣着再给、给完就撤，收益主要来自"少添乱"；同样的内容帮了中等模型，却拖累了最强的模型
- 是否给 agent 挂记忆，要看接收的是哪个模型；建议每换一个模型先做一个不带记忆的小试点

**需要说清楚的边界**

- 作者自己承认的（第 6 节）：只是从固定的经验池里一次性复用，没做"自己跑完的记录再存回去"，也没处理过时和矛盾；"卡住了"只用了一个手写信号（第一次验证失败）；撤掉的只是实现记录本身，agent 对它的回应还留在历史里；覆盖率只证明出现过，不证明因果；多数非 REM 条件只跑了 1 遍；其他记忆系统的检索数字是从基准论文里抄的、各用各的配置，没在同一套向量模型和重排下重跑；99 题的相关记录全部来自同一个仓库，没测过时记录、也没比对存下的修法和标准答案有多像
- 修复率的提升很小：+2.7 个点，p=0.22 不显著；不给记忆这一条件自己重跑三遍就在 23～26 题之间晃。可靠的是检索准确率（领先 13 个点）和成本下降，"修复率更高"只能当方向
- "对最强的模型有害"这一条，每个模型只跑了 1 遍，作者自己说只看正负号的规律
- 收益主要来自四阶段文档本身，"卡住再给、给完就撤"在 Sonnet 4.5 上只是不让实现记录添乱；换其他 4 个模型，只给文档在 3 个上不比完整 REM 差（第 5.4 节）
- 只测了修 bug 这一类，有"定位、理解、修复、验证"四个阶段的诊断型任务；作者说能推广到 SQL 修复、故障排查，但只测了字段生成
- 用的全是 Anthropic 的模型（Haiku 4.5、Sonnet 4.5、Opus 4.6、Opus 4.8、Sonnet 5），向量模型是亚马逊自家的；作者全部在亚马逊任职，声明无利益冲突
- 是研讨会论文，篇幅短，没给代码
- 和库里已存的 Zhou 2026（《agent 的记忆先存原始轨迹，等新任务来了再现场整理》）方向相反：那篇主张存原始记录、用的时候再整理，这篇主张存的时候就压成四阶段文档、原记录只在卡住时给一次。两篇用的基准和任务不同，谁对要看场景，整理时可以对照着看
