# AIエージェントを司令官と部下に分けて、開発を自律運用してみた（2）司令官と部下の役割設計

> この記事は、下書きと文章の整理に生成AIを使っています。内容は、著者が生成AIを使ってタスクを自律的に回し続けるやり方を実際に試して検証し、そのやり方と感想を記録したものです。

この回では、1つのプロジェクトの中で「誰が何をしてよいか」をどう決めたかを書きます。このリポジトリでは、メインのセッションを司令官にして、実装・検証・調査をそれぞれ別のサブエージェントに任せています。役割は文章で決めるだけでなく、定義ファイルのツール欄とモデル欄でも制約をかけています。この回だけ読んでも、自分のプロジェクトで役割を分けるときの型を持ち帰れるように書きます。

## 4つの役割

CLAUDE.md の「役割」の節には、次の4つが書かれています。

| 役割 | モデル | 担当 | 触れるもの |
|---|---|---|---|
| 司令官（メインセッション） | Opus | 計画・分担・検証・記録 | 全体（大きな実装は自分でしない） |
| worker | Sonnet | 実装 | ファイルの読み書き、Bash。ウェブ系のツールは持たない |
| reviewer | Sonnet | worker の変更を検証し、合格か要修正かを判定 | 読み取りと Bash（ファイルは変更しない決め） |
| researcher | Haiku | 調査 | 読み取りとウェブ。ファイルの書き込み・コマンド実行は不可 |

司令官の仕事は「計画・分担・検証・記録」の4つに絞り、CLAUDE.md には「大きな実装は自分でせず worker に任せる」と書きました。実装を別のサブエージェントに出し、司令官は「何を、どの順で、どう確かめるか」を受け持つ、という分け方です。

人間のチームと同じように、AIモデルにも能力に応じて役割を分け、タスクを分担させることで、それぞれが1つのタスクに集中して取り組めるようになります。

## 定義ファイルで権限を決める

サブエージェントは `.claude/agents/` の Markdown ファイルで定義します。先頭の front matter にモデルと使えるツールを書き、本文に指示を書きます。実物を見ていきます。

### worker

```
---
name: worker
description: 計画のうち独立した実装タスクを1つ担当する。コードの作成・修正・テスト実行を任せるときに使う。互いに独立したタスクは複数の worker に並列で任せてよい。
model: sonnet
tools: Read, Edit, Write, Bash, Grep, Glob
maxTurns: 50
isolation: worktree
---
あなたは司令官から渡されたタスクを1つだけ実装する担当です。

- 渡された範囲の外にあるファイルは変更しない。必要だと判断したら、変更せずに報告に書く。
- 実装したら、関連するテストやビルドを実行して結果を確かめる。テストを消したり弱めたりして通さない。
- 判断に迷う点は、もっとも妥当な案で進め、その判断を報告に書く。
- あなたは専用の git worktree で動いている。作業を終えたら、その worktree のブランチにコミットする（push はしない）。
```

ポイントは3つです。

- 「1つだけ」: 1回の呼び出しで、タスクは1つ。範囲の外は触らず、必要なら報告に書かせます。
- `tools` にウェブ系のツール（WebFetch・WebSearch）が無い。worker は実装に使うツールだけを持ちます。
- `isolation: worktree`: 専用の git worktree で動かします。この分離で起きたことは、次回（第3回）に書きます。

### reviewer

```
---
name: reviewer
description: worker が実装した変更を検証するレビュー役。バグ、要件の取りこぼし、テスト不足を確認し、完了と判断してよいかを判定させるときに使う。
model: sonnet
tools: Read, Grep, Glob, Bash
maxTurns: 30
---
あなたは司令官のための検証担当です。ファイルは変更しません。Bash はテスト・ビルド・git diff などの確認にだけ使います。
```

定義ファイルの本文には、このあとに検証の手順が続きます（後半で扱う予定です）。報告の形は次のように決めています。

1. 判定: 合格 / 要修正
2. 要修正の場合: 問題点ごとに、ファイルと行、起きること、直し方の方針
3. 実行した確認コマンドと結果

reviewer のツール欄には Edit と Write がありません。ただし Bash は使えるので、「ファイルは変更しない」はツール欄だけで保証されるものではなく、定義ファイルの指示に頼る部分があります。

### researcher

```
---
name: researcher
description: コードベースの調査やウェブでの情報収集を担当する読み取り専用の調査役。ファイルの場所探し、仕組みの把握、ドキュメントや仕様の確認を任せるときに使う。
model: haiku
tools: Read, Grep, Glob, WebFetch, WebSearch
maxTurns: 30
---
あなたは司令官のための調査担当です。ファイルの変更やコマンドの実行はしません。

- 聞かれたことに答えるのに必要な範囲だけを調べる。
- 根拠となるファイルのパスと行番号、またはウェブページの URL を必ず添える。
- 確認できたことと、推測にすぎないことを分けて書く。
```

researcher は Edit・Write・Bash を持たず、代わりにウェブを調べられます。報告には根拠（パスと行番号、または URL）を必ず付け、「確認できたこと」と「推測」を分けさせています。

### 一覧にすると

| 定義ファイル | モデル | ツール | maxTurns |
|---|---|---|---|
| worker.md | sonnet | Read, Edit, Write, Bash, Grep, Glob | 50 |
| reviewer.md | sonnet | Read, Grep, Glob, Bash | 30 |
| researcher.md | haiku | Read, Grep, Glob, WebFetch, WebSearch | 30 |

## 制約が運用を決めた

この分け方は、運用の形を決めました。worker はウェブを調べられず、researcher はファイルを書けません。つまり、調査の結果をそのままファイルにしてくれる役がいません。

PROGRESS.md の「ゴールの決定と第1段階の開始」には、調査の進め方がこう書かれています。

> worker はウェブを調べられず、researcher はファイルを書けない。そこで、司令官が researcher（真偽の判断があるので model は sonnet を指定）と claude-code-guide に調べさせ、報告書は司令官が research/ にまとめる。形式の確認は T1 の検査ツール、内容の確認は reviewer が行う。

流れにすると、次のとおりです。

1. 司令官が researcher に調査を依頼する。
2. researcher が根拠付きで報告を返す。
3. 司令官が報告を research/ のレポートにまとめる。
4. 形式は検査ツール（T1）が、内容は reviewer が確かめる。

調査の内容は researcher、レポートの形は司令官、確認は別の担当、という分担になります。

モデルは、仕事の性格で使い分けています。CLAUDE.md には「真偽の判断がある調査は、呼び出し時に `model: "sonnet"` を指定する。場所探しのような単純な調査は、既定の haiku のまま」と決めています。定義ファイルの haiku を、呼び出し時に上書きするわけです。

モデルを使い分けたことで、トークンの使用量が増えるのを、はっきり抑えられたと感じています。難しい判断は Opus に任せ、単純な作業は Sonnet と Haiku で実行します。Sonnet と Haiku の実行結果は、さらに Opus が整理してまとめるので、質の面でも問題は感じませんでした。

### 公式ドキュメントとの対応

この回に関係する公式ドキュメントの記述のうち、このプロジェクトの調査で確認したものを挙げます。

- サブエージェントのモデルは、呼び出し時の指定、定義の `model`、環境変数、親のモデルの順で決まります。researcher を呼び出し時に sonnet に上書きできるのは、この順序によります（[Subagents](https://code.claude.com/docs/en/sub-agents.md) の「Model resolution order」）。
- エージェントごとにモデルを使い分けることについて、公式は、大半のコーディングは Sonnet で足り、Opus は設計や多段の推論に、単純なサブエージェントには Haiku を、と書いています（[Costs](https://code.claude.com/docs/en/costs.md)）。
- 書いた本人とは別の、新しいコンテキストのレビュー役を使うことは、公式の推奨です。ただし同じページが、レビュー役は何かしら指摘しがちなので、正しさと要件に関わるものだけを挙げるよう指示せよ、とも書いています（[Best practices](https://code.claude.com/docs/en/best-practices.md)）。
- 定義ファイルの front matter の未知の項目は、エラーにならず無視されます（[Subagents](https://code.claude.com/docs/en/sub-agents.md)）。項目名のタイプミスには気づきにくいので、書いたあとに期待どおり効いているかを確かめる必要があります。

役割を分けると、いつも得をするとは限りません。マルチエージェントにすると、トークンは大幅に増えます（[Anthropic のマルチエージェントの調査システムの記事](https://www.anthropic.com/engineering/multi-agent-research-system)）。「並列にすれば速くて安い」ではなく、速いが高い、というのが調査での判定でした。

## 「1サイクルの進め方」を文章で固定する

役割を分けただけでは、毎回の動かし方がぶれるかもしれません。そこで CLAUDE.md に、司令官の1サイクルの手順を番号付きで固定しました。要点を6つにまとめると、次のとおりです。

1. PROGRESS.md、tasks.json、`git log --oneline -20` を読んで現状を把握する。
2. `passes: false` のタスクのうち、前提のタスクが済んでいて互いに独立したものを選ぶ。
3. 選んだタスクを worker に1つずつ渡し、同じターンでまとめて並列に起動する。各 worker には、タスクの id・受け入れ条件・触ってよい範囲を伝える。
4. worker の報告が戻ったら、reviewer に検証させる。要修正なら、同じ worker に差し戻す。
5. 合格したブランチを main にマージし、tasks.json を更新して、PROGRESS.md に追記してコミットする。
6. すべてのタスクが `passes: true` になるまで繰り返す。

この手順には、役割分担を支える考え方が3つ入っています。

- 完了を決めるのは worker ではない: worker の報告が戻っても、すぐには完了になりません。tasks.json の `passes` は、reviewer が合格を出したものだけを `true` にします。
- 渡すときに範囲を伝える: タスクの id、受け入れ条件、触ってよい範囲を、毎回 worker に渡します。worker の定義にある「範囲の外は変更しない」と対になっています。
- 並列にするのは独立したものだけ: 前のタスクに依存するタスクは、そのマージが済んでから渡します。

受け入れ条件は、tasks.json の各タスクに `acceptance` として「実行して確かめられる確認コマンド」を書き、終了コード0で合格とみなします。受け入れ条件の落とし穴と reviewer の判定は、後半で書く予定です。

## この回の持ち帰り

自分のプロジェクトで役割を分けるときは、次の順で考えると進めやすいと思います。

1. 役割ごとに「何をしてよいか」を、ツール欄で決める。書ける・読めるだけ・ウェブを調べられる、のどれかを選ぶ。
2. 役割ごとにモデルを決める。考える量の多い仕事と、単純な仕事を分ける。
3. 「誰が完了を決めるか」を、実装した本人以外にする。
4. 毎回の手順を、番号付きの文章で固定する。会話が切れても、同じ手順に戻れる。
5. 制約から生まれる不便（調査の結果を誰がファイルにするか、など）を、運用の手順として明記する。

このプロジェクトでは、このように役割を分けたことで、速度と品質の両方を高く保ちながら、並列で効率よくタスクを進められたと感じています。さらに、より高性能なモデル（Fable）をアドバイザーとして起用し、Opus でも判断が難しい部分を判断させれば、より難しいタスクの品質も高められるかもしれません。
